### 1.2. Problem Statement

Server tự chụp và lưu draft roster/Ready/pha lobby sau mỗi thay đổi hợp lệ.
Do save chạy bất đồng bộ, một request cũ có thể hoàn tất sau request mới.
Cần lưu đúng snapshot hợp lệ mới nhất theo revision, kể cả khi tranh chấp,
revision trùng, payload lỗi, hủy tác vụ hoặc ghi file thất bại giữa chừng.

### 1.3. AC, NFC và invariant

| ID | Tiêu chí kiểm chứng |
|---|---|
| AC1 | Join/Ready/phase change tự capture DTO bất biến và lưu; public Read trả snapshot hoàn chỉnh, không cần nút Save |
| AC2 | Theo RoomId, revision chỉ tăng; save cũ/trùng không đổi state. Revision trùng chỉ một commit, winner đầu tiên giữ ổn định khi retry |
| AC3 | Null/empty/schema sai/revision ≤0/player-slot sai bị từ chối; I/O/cancel trước publish giữ bản trước và cho retry |
| AC4 | 40 task vẫn giữ revision hợp lệ lớn nhất; reopen/các instance backend giữ invariant; archive không trao quyền live Ready/host |
| NFC1 | Concurrency safety và p95 ≤1.500 ms cho 40 task; công bố p50/p95/p99/max, backend và phạm vi đo |
| NFC2 | Bảy asmdef không vòng, Domain không engine; lịch test bằng tín hiệu, không reflection vào private field hoặc phụ thuộc clock freshness |

**Monotonic Freshness Invariant:** incoming được phép thay current iff
`incoming.IsValid() && incoming.Revision > current.Revision`; chưa có current
xem như revision 0. I/O failure không phải commit. Read/compare/stage/publish
nằm trong cùng lease theo key; không thả khóa trước `await CommitAsync`.

DTO: schema 1; RoomId 1–64 ký tự không trắng, revision long dương; phase
Waiting/Loading/Playing; 1–4 member, ID không trắng/trùng, slot 0–3 không trùng,
tối đa một host. RoomId phân biệt hoa/thường. Phiên mới dùng Guid mới, không dùng
connection ID hoặc UTC làm version; lobby rỗng không ghi snapshot rỗng mới.

### 1.4. Hai phương án và lựa chọn

| Tiêu chí | A — UTC + write rời rạc | B — revision + transaction |
|---|---|---|
| Version | Timestamp có thể trùng/đảo khi clock thay đổi | long tăng theo stream, không cần đồng bộ đồng hồ |
| Race | Check trước, async write sau; completion cũ có thể thắng | Compare/write cùng lease, atomic publish |
| I/O | PlayerPrefs hoặc overwrite trực tiếp có thể torn write | Temp + flush + replace cùng filesystem |
| Kiểm thử | Sleep, timing và Unity khó cô lập | TCS/barrier, immutable DTO, NUnit engine-free |
| Phù hợp repo | Không tận dụng boundary server/domain hiện có | Domain lõi; Server capture Mirror/main thread và System.IO |

**Chọn B.** Không kết luận mọi thiết kế timestamp đều sai: một timestamp được
phối hợp bằng sequence/CAS có thể đúng, nhưng lúc đó đã cần thêm cơ chế ordering
và atomicity tương tự B. A như đề xuất ban đầu thiếu cả hai.

Review/sửa giả định AI bằng mã repository:

1. Đề xuất tạo `Core/Gameplay/Client.UI` assembly bị bác bỏ: asmdef thực là
   Shared.Domain, Shared.Protocol, Networking, Server, Client và hai test assembly.
   EditMode chỉ tham chiếu Domain; thêm dependency Unity vào đó sẽ phá engine-free.
2. Đề xuất dùng PlayerPrefs/path Unity trong Task.Run bị sửa: ServerLobbyController
   capture members và `Application.persistentDataPath` trên main thread; worker
   chỉ nhận DTO/path. Không dùng Unity API làm kho dữ liệu server song song.
3. Đề xuất mở room 40 player bị bác bỏ: `LobbyRoom.Capacity=4`; load là 40 save
   task tranh chấp, giữ nguyên sức chứa và host/all-ready guard M2.
4. Đề xuất restore Ready/host từ file bị bác bỏ: connection đang sống vẫn do
   server xác thực; archive chỉ là draft, không gọi SetReady/TryStart khi load.
5. Đề xuất test assert private lock/count hoặc cố định thứ tự ThreadPool bị sửa
   thành public Save/Read, exactly-one commit và cuối cùng max revision hợp lệ.

### 1.5. Vertical slice đã chọn

Domain: LobbyDraftSnapshot, LobbyDraftMember, DraftSaveResult, storage/transaction
contract, InMemoryDraftStorage và AutoSaveDraftService. Server/Sessions:
LobbyDraftAutoSave và AtomicFileDraftStorage, gọi từ Publish của ServerLobbyController.
Không thêm UI/save button, network Command hay asmdef; không đổi scene/prefab/combat.

Lease memory nằm ở backend nên hai service chung backend vẫn đồng bộ. Backend
file lấy OS-exclusive lease, đọc bản đã commit sau khi lấy lease, giữ lease đến
sau flush/atomic replace; nhiều backend instance dùng cùng thư mục vẫn an toàn.
Temp file cùng thư mục, tên key hash SHA-256 để payload không chọn đường dẫn.
Reader kiểm tra header/schema/validation và fail-closed với file hỏng.
Cancellation được xét trước publish; sau publish không báo canceled giả vì data
đã commit. Timeout lease 5 giây phục vụ liveness, không dùng clock để xét freshness.

### 3.2. Patch tối thiểu của hợp đồng

```csharp
if (snapshot == null || !snapshot.IsValid()) return DraftSaveResult.RejectedInvalid;
using (var transaction = await storage.OpenAsync(snapshot.RoomId, cancellationToken).ConfigureAwait(false))
{
    if (transaction.Current != null && snapshot.Revision <= transaction.Current.Revision)
        return DraftSaveResult.RejectedStale;
    await transaction.CommitAsync(snapshot, cancellationToken).ConfigureAwait(false);
    return DraftSaveResult.Saved;
}
```

Thay đổi cốt lõi là hai guard ở đúng boundary, không chỉ dictionary thread-safe.
Adapter và backend phục vụ vertical slice thật: chụp snapshot trước await, stage/
flush/replace thay ghi đè trực tiếp, lease bao trọn commit để hai writer không
cùng thấy revision cũ. Không chuyển luật room/combat vào worker hoặc UI.

### 4.3. Flaky-test audit

1. **Thread scheduling:** không Sleep để áp thứ tự; TC04 dùng tín hiệu rõ ràng.
   TC06 không assert ID winner. Test green max40 đúng với mọi lịch; việc một
   mutant có thể tình cờ pass TC05 không làm TC03/04/06 mất tính xác định.
2. **Shared state và singleton Unity:** mỗi contract test có backend mới, file
   test có Guid directory; fixture lobby reset Mirror/transport. Test inject
   memory storage trước Host để không ghi AppData chung trong regression.
3. **Clock drift/performance noise:** revision độc lập UTC; Stopwatch monotonic
   đo latency. CPU/JIT/disk/antivirus có thể đổi p95, nên ghi backend/môi trường,
   không sửa ngưỡng hoặc retry chỉ để lấy số đẹp. Kết quả instrumented không làm SLO.
4. **Filesystem/platform:** TC17 dựa FileShare/Replace Windows như CI windows-2022;
   Linux cần fault seam khác, không suy kết quả này cho mọi filesystem/điện mất.

### 5.3. Reflection — bản nháp có AI hỗ trợ, sinh viên tự rà soát

Qua bài toán này, tôi nhận thấy việc một hàm trả về thành công chưa đủ chứng minh dữ liệu được bảo vệ. Điều quan trọng là snapshot nào còn tồn tại sau khi nhiều yêu cầu cạnh tranh hoàn tất. Nếu chỉ kiểm tra đường đi thuận, một chương trình ghi mọi revision vẫn có thể vượt qua các bài test nhìn khá thuyết phục.

Tôi cần phân biệt thứ tự chỉnh sửa với thời điểm tác vụ kết thúc. Revision mô tả thứ tự mong muốn; đồng hồ chỉ phục vụ đo hiệu năng. Tín hiệu điều phối giúp tái hiện trường hợp bản cũ đến sau mà không phải hy vọng scheduler chạy đúng như một khoảng Sleep dự đoán.

Điểm đáng chú ý là AI có thể viết một assertion tưởng hợp lý nhưng gắn với cách triển khai. Kỳ vọng số revision không đổi sau Leave đã bỏ qua việc disconnect cũng là thay đổi roster hợp lệ. Sửa test theo bất biến giúp giữ hành vi sản phẩm đúng, thay vì sửa sản phẩm để chiều test.

Thử nghiệm mutation làm rõ giới hạn của coverage. Dù nhiều dòng mã được chạy, oracle sai vẫn có thể chấp nhận stale write. Việc bỏ guard và quan sát các case concurrency thất bại cung cấp bằng chứng trực tiếp hơn một tỷ lệ đẹp đứng riêng.

Kết quả tải cũng cần được diễn giải đúng phạm vi. Bốn mươi task lưu không phải bốn mươi người chơi trong một phòng bốn slot. Số đo memory và disk phải tách riêng, có môi trường, percentile và giới hạn. Trước khi nộp, tôi sẽ tự rà soát báo cáo, chạy lại các lệnh và điều chỉnh phần phản tư này theo trải nghiệm thực tế của mình.
