# ADR-065-01 — One authoritative owner and local atomic transaction

Status: accepted for the individual experiment; not a team production decision.

Context: default main contains only README. Supplied SRS v0.2 identifies Unity offline
MVP and future authoritative multiplayer. AD-065 adds a failed schema deployment,
764 concurrent tasks, p95 <=4.5 s, operational retention 7 days and change-request
response obligation 12 hours. Single-student scope needs executable evidence.

Decision: modular monolith; domain owns rules, application coordinates a structural
UnitOfWork, SQLite Store owns persistent tables and the BEGIN IMMEDIATE/COMMIT boundary.
One transaction includes HP, permanent command identity/response and durable event.
Keep app v1/v2 compatible through nullable additive event metadata; rollback the app,
retain schema/data. Do not run destructive DOWN. Retention deletes operational events
only. The 12 hours is a response obligation, not a migration or completion deadline.

Alternatives: combat service plus asynchronous event worker/broker can independently
deploy projections but introduces delivery, deduplication, queue latency and contract
versioning work. PostgreSQL async adapter is a viable future implementation of the
selected monolith; it has not been tested here. No distributed transaction is required.
Full comparison across performance, consistency, modifiability, deployability, rollback,
complexity, operations and team capacity appears on report page 4.

Rationale: local atomicity is more directly testable than a distributed saga for this
feature; production scalability benefits of splitting have not been established.
Available Node/SQLite supports a real file database with no runtime dependencies.
This does not claim alignment with a mandated backend stack: the SRS mandates none.

Consequences: high cohesion of rules, domain independent of HTTP/SQL; simple rollback
compatibility. Synchronous SQL blocks the event loop; FULL durability costs disk latency.
Permanent identities grow. Observer is best effort, repeated on successful replays;
mandatory external effects would require a durable outbox. One writer per DB assumed.

Evidence: implementation 1ff1033; tests/final-tests.txt (10 pass), rollback/result.md;
performance/load.json (p95 583.7435 ms, 764 tasks, 7640 samples, 0 errors, short local run).
Not evidence of WAN, multi-writer, PostgreSQL or sustained production capacity.

Review triggers (proposed): two representative 5-minute 764-task runs with p95 >4.5 s
or errors >0.1%; event-loop lag p95 >50 ms for 5 minutes; explicit independent-writer
requirement on shared matches; or command identities >1 GB per DB. Measure contention
before choosing PostgreSQL, match sharding or service separation. No such trigger is
claimed to have been measured. Full 12-hour operational workflow is unverified.
